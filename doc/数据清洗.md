# 门店销售数据清洗计划

## 1. 清洗目标

将原始 POS 导出数据转换为可用于后端 API、数据看板和 AI 问答的标准化数据，同时保留原始数据、异常记录和清洗过程，确保结果可追溯、可复现。

清洗原则：

- 原始 CSV 只读，不直接覆盖。
- 清洗脚本可重复执行，相同输入产生相同结果。
- 不确定的数据不擅自猜测，进入异常区等待确认。
- 每条被修正、删除或隔离的记录都有原因和来源行号。
- 分析指标只基于清洗后、通过必要校验的数据。

## 2. 数据分层

```text
data/raw/          原始 CSV，只读保存
data/clean/        标准化后的有效数据
data/quarantine/   无法确认或校验失败的异常记录
data/reports/      清洗报告、统计摘要和校验结果
```

计划处理的原始文件：

| 文件 | 类型 | 主要用途 |
|---|---|---|
| `sales.csv` | 销售事实表 | 订单、日期、门店、商品、数量、金额、支付方式 |
| `stores.csv` | 门店维表 | 门店名称、门店品类、区域 |
| `products.csv` | 商品维表 | 商品名称、商品品类、单价 |

## 3. 导入前检查

每次导入记录以下信息：

- 文件名、文件大小、导入时间
- 原始文件哈希值
- 文件编码和分隔符
- 表头及列数
- 原始数据行数
- 清洗脚本版本

CSV 结构检查包括：

- 文件是否存在、是否为空
- 表头是否符合预期
- 每行列数是否一致
- 是否存在空行、多余列或缺失列
- 是否存在无法解析的 CSV 行

结构不符合要求的行进入异常记录，不让导入过程静默跳过。

## 4. 通用文本标准化

对所有文本字段执行：

- 去除首尾空格
- 清理不可见字符
- 统一全角/半角字符
- 空字符串转换为 `NULL`
- ID 字段统一大写，例如 `s01` 转为 `S01`

门店名和商品名只做空白及字符规范化，不进行未经确认的模糊合并，避免将不同商品错误合并。

## 5. 日期字段清洗

原始销售数据存在多种日期格式，明确支持：

- `YYYY-MM-DD`
- `YYYY/MM/DD`
- `DD-MM-YYYY`

统一输出字段：

```text
date_raw       原始日期
date_clean     标准日期，格式 YYYY-MM-DD
date_status    日期处理状态
```

处理规则：

- 能按明确格式解析的日期统一为 `YYYY-MM-DD`。
- 无法解析的日期进入 `quarantine`。
- 不自动猜测 `MM-DD-YYYY` 与 `DD-MM-YYYY` 的歧义。
- 检查日期是否为空、是否超出业务时间范围、是否为未来日期。
- 清洗报告记录最小日期、最大日期及各日期格式的数量。

## 6. 数值字段清洗

### 6.1 `qty` 数量

- 去除空格并转换为数值类型。
- 正常销售数量必须大于 0。
- `qty = 0` 进入异常区。
- `qty < 0` 保留并标记为退货/冲销候选记录。
- 非数字值、缺失值进入 `quarantine`。

建议保留字段：

```text
qty_raw
qty_clean
qty_status
```

### 6.2 `amount` 金额

- 去除 `¥`、`￥`、千位分隔符和首尾空格。
- 使用 Decimal 或定点数存储，不使用浮点数作为最终金额类型。
- 统一保留两位小数。
- 缺失金额不补 0，进入异常区并统计影响范围。
- `amount < 0` 保留并标记为退款/冲销。
- 非法货币格式进入 `quarantine`。

建议保留字段：

```text
amount_raw
amount_clean
amount_status
```

### 6.3 `unit_price` 单价

- 转换为 Decimal 并保留两位小数。
- 单价必须大于 0。
- 检查 `amount` 与 `qty * unit_price` 是否存在明显差异。
- 差异可能来自折扣，因此只产生告警，不直接覆盖销售金额。

## 7. 主键、重复与冲突处理

### 7.1 门店维表

`stores.store_id` 必须唯一：

- 完全相同的重复门店可去重并记录。
- 同一 ID 对应不同名称、品类或区域时，不自动选择，进入人工核查列表。

### 7.2 商品维表

`products.product_id` 必须唯一：

- 完全相同的重复商品可去重并记录。
- 同一 ID 对应不同商品名或单价时，进入人工核查列表。

### 7.3 销售明细表

不能只按 `order_id` 去重，因为一个订单可能包含多个商品。

处理级别：

1. 完全相同的整行重复：删除重复副本。
2. `order_id + product_id + date + store_id + qty + amount + payment` 完全相同：标记为重复候选。
3. 同一订单下的多条不同商品明细：保留。
4. 同一订单号对应不同日期、门店或金额：标记为订单冲突，不自动合并。

每个去重或隔离结果记录：

```text
source_file
source_row
record_key
duplicate_group_id
reason
```

## 8. 外键完整性

销售表必须分别关联门店表和商品表：

- `store_id` 不存在于 `stores`：隔离并记录 `INVALID_STORE_FK`。
- `product_id` 不存在于 `products`：隔离并记录 `INVALID_PRODUCT_FK`。
- 两个外键都有效：进入清洗后的销售事实表。
- 不使用“未知门店”或“未知商品”静默填充。

清洗后的事实表应能直接获得：

- 门店名称、门店品类、区域
- 商品名称、商品品类、单价

## 9. 业务规则校验

- `order_id`、`date_clean`、`store_id`、`product_id` 不为空。
- `qty_clean` 不能为 0。
- `amount_clean` 必须是合法金额。
- 支付方式属于已知集合，未知值保留原文并产生告警。
- 销售日期处于统一业务时间范围内。
- 对数量、金额进行极端值检查。
- 同一订单的多条明细汇总应可解释。

当前已知支付方式枚举：

```text
微信
支付宝
会员储值
银行卡
现金
```

## 10. 异常记录规范

异常记录至少包含：

```text
source_file
source_row
record_key
field_name
raw_value
error_type
error_message
severity
```

建议的 `error_type`：

```text
MISSING_VALUE
INVALID_DATE
INVALID_NUMBER
NEGATIVE_QTY
NEGATIVE_AMOUNT
INVALID_STORE_FK
INVALID_PRODUCT_FK
DUPLICATE_ROW
CONFLICTING_DIMENSION
UNKNOWN_PAYMENT
```

严重等级：

- `ERROR`：不能进入分析数据。
- `WARNING`：可以进入分析，但必须在报告中提示。
- `INFO`：已自动规范化或修正。

## 11. 分析指标口径

第一版统一采用以下口径：

- 营业额：有效销售记录的 `SUM(amount_clean)`，负金额保留。
- 订单数：`COUNT(DISTINCT order_id)`。
- 客单价：营业额除以订单数。
- Top 10 商品：按商品名称 JOIN 后的销售额排序。
- 品类营业额：根据明确的商品品类或门店品类分别统计，不混用。
- 无效外键记录：不参与门店或商品排行，但在数据质量报告中展示。
- 退款/冲销：保留原记录，并单独统计退款金额及笔数。

这些口径必须同时用于 API、前端图表和 AI 问答，避免出现数字不一致。

## 12. 清洗报告

每次清洗至少输出：

```text
原始行数
有效行数
隔离行数
自动修正行数
去重行数
缺失值数量
无效门店外键数量
无效商品外键数量
负数量记录数量
负金额记录数量
日期最小值/最大值
总营业额
订单数
```

报告应支持按文件、字段、异常类型和严重等级查看。

## 13. 验收标准

- 原始 CSV 未被修改。
- 清洗脚本可重复运行。
- 相同输入每次生成相同结果。
- 清洗后金额和日期均可被程序稳定解析。
- 所有进入分析的数据都能关联到有效门店和商品。
- 每个异常记录都有明确原因和来源行号。
- 去重不会误删同一订单中的不同商品明细。
- 清洗后总营业额、订单数和客单价可以由明细重新计算得到。
- 关键统计结果有自动化测试或独立 SQL 校验。

## 14. 实施顺序

1. 创建原始、清洗、异常和报告目录。
2. 实现 CSV 结构检查和导入日志。
3. 实现文本、日期、数量、金额标准化。
4. 实现维表主键和销售明细去重检查。
5. 实现门店、商品外键校验。
6. 实现业务规则校验和异常分类。
7. 生成清洗后的数据文件及数据质量报告。
8. 用清洗结果计算营业额、订单数、客单价，确认指标口径。
9. 编写重复执行测试和关键统计校验，为后端 API 接入做准备。
