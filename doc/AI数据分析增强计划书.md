# AI 数据分析增强计划书

## 1. 项目目标

在现有 React 看板、FastAPI 后端、LangChain 问答和 SQLite 清洗数据源基础上，增强 AI 数据分析能力，使系统具备可靠的上下文追问、可证明的数字一致性、AI 与图表联动、门店对比、流式回答和生产部署能力。

核心原则：

- `data/clean/sales_clean.sqlite` 是业务数字的唯一事实来源。
- LangChain 只负责解析意图和组织表达，不执行任意 SQL，不自行计算业务指标。
- 所有查询均由后端白名单查询函数执行。
- AI 最终回答中的营业额、订单数、客单价、销量等数字必须能在 `facts` 中找到，并与数据库查询结果一致。
- LLM 不可用时降级到本地规则解析和模板回答，不影响真实数据查询。

## 2. 上下文追问

### 2.1 目标

支持多轮对话中的条件继承和局部修改。例如：

```text
用户：牛肉poke 六月卖了多少钱？
AI：牛肉poke 在 2026 年 6 月的净营业额为……
用户：那五月呢？
AI：继承“牛肉poke、净营业额”，仅将日期改为 2026 年 5 月。
用户：换成三文鱼poke呢？
AI：继承 2026 年 5 月和净营业额，仅替换商品。
用户：S01 门店呢？
AI：继续继承日期、商品和指标，增加门店条件。
用户：订单数呢？
AI：继承日期、商品和门店，仅将指标改为订单数。
```

### 2.2 上下文模型

新增结构化 `ConversationContext`：

```text
intent
metric
start_date
end_date
store_id
product_name
category
dimensions
comparison_targets
previous_message_id
```

每次问答按“读取上一条成功计划 -> 解析本轮增量 -> 合并 -> 校验 -> 查询”的顺序执行。

### 2.3 合并规则

- 本轮明确提供的字段覆盖上一轮字段。
- 本轮未提供的字段根据意图决定是否继承。
- “那五月呢”只替换日期，不丢失商品、门店和指标。
- “换成 S02”只替换门店。
- “订单数呢”只替换指标。
- 新的完整问题可以重置不相关上下文。
- `unsupported`、`no_data`、`provider_error` 且未成功查询的消息不能覆盖有效上下文。
- 指代存在多个合理解释时返回 `clarification_required`，不得猜测。

### 2.4 LangChain 职责

LangChain 输出本轮的结构化增量计划，包括：

```text
operation: inherit | replace | clear
changed_fields
intent
metric
filters
confidence
```

后端负责合并和校验。模型不得直接修改持久化上下文，不得返回或执行 SQL。

### 2.5 前端展示

AI 回答下方展示本轮实际使用的条件：

```text
时间：2026-05-01 至 2026-05-31
商品：牛肉poke
门店：S01
指标：订单数
继承条件：商品、门店
```

当需要澄清时提供可点击选项，用户选择后继续同一对话。

## 3. AI 数字可信度自动化测试

### 3.1 目标

建立独立真值计算与 AI API 对照测试，证明：

```text
AI 回答中的业务数字 = facts 中的数字 = SQLite 独立查询结果
```

固定测试集的数字一致率必须为 `100%`。

### 3.2 测试链路

```text
固定 SQLite 测试数据
  -> 独立 SQL 计算期望值
  -> 调用 AI 问答 API
  -> 校验 query plan
  -> 校验 facts
  -> 提取最终回答中的业务数字
  -> 与数据库真值逐项比较
  -> 生成验证报告
```

真值 SQL 与 AI 业务查询服务分开实现，避免测试重复调用被测函数而产生假通过。

### 3.3 测试矩阵

- 指定周期净营业额。
- 去重订单数。
- 客单价等于净营业额除以订单数。
- 商品营业额、销量和订单数。
- 门店营业额及排名。
- 品类营业额及排名。
- Top 商品稳定排序。
- 负金额退款计入净营业额。
- 无交易日期与空区间。
- “那五月呢”等上下文追问。
- 替换商品、门店和指标的连续追问。
- 门店或商品对比。
- 不存在的商品返回 `no_data`，不生成数字。
- 不支持的利润、成本等问题返回 `unsupported`。
- 模型返回错误数字时丢弃模型文本并切换模板回答。
- 回答中不得出现 `facts` 之外的业务数字。

### 3.4 报告产物

新增：

```text
data/reports/ai_answer_verification.json
```

每条记录包含：

```text
case_id
question
conversation_history
query_plan
expected_database_facts
actual_facts
final_answer
numbers_in_answer
consistency_passed
fallback_used
duration_ms
```

同时生成 pytest/JUnit 结果供 CI 判断。真实 LLM 联网测试使用单独标记，日常测试默认使用可控的模型桩，避免网络波动影响验收。

## 4. AI 与看板图表联动

### 4.1 响应契约

AI 查询响应新增：

```json
{
  "dashboard_target": {
    "start_date": "2026-05-01",
    "end_date": "2026-05-31",
    "store_id": "S01",
    "metric": "net_revenue",
    "view": "trend"
  }
}
```

`dashboard_target` 必须由已经校验的查询计划生成，不能直接采用 LLM 原始输出。

### 4.2 前端交互

AI 回答增加“在看板中查看”按钮，跳转到：

```text
/?start_date=2026-05-01&end_date=2026-05-31&store_id=S01&metric=net_revenue&view=trend
```

看板加载后：

- 解析并校验 URL 参数。
- 自动应用日期和门店筛选。
- 自动请求对应看板数据。
- 滚动到目标图表并短暂高亮。
- URL 保留筛选状态，支持刷新、分享和浏览器前进后退。
- 无效日期、门店或视图参数显示提示，不静默套用。

## 5. 门店对比视图

### 5.1 后端

新增 AI 意图：

```text
store_comparison
```

新增接口：

```text
GET /api/v1/dashboard/store-comparison
```

参数：

```text
start_date
end_date
store_ids：2 至 5 家门店
```

返回每家门店的：

- 净营业额。
- 订单数。
- 客单价。
- 每日趋势。
- Top 商品。
- 与对比组平均值的差异。

### 5.2 前端

新增 `/comparison` 页面，采用：

- 门店多选器，限制 2 至 5 家。
- 并列 KPI。
- 多折线趋势图。
- 差异表。
- 商品结构对比。

AI 回答门店比较问题后提供“打开门店对比”按钮，并携带本轮日期与门店参数。

## 6. 流式输出

### 6.1 技术方案

使用 Server-Sent Events（SSE），新增：

```text
POST /api/v1/ai/query/stream
```

事件顺序：

```text
status
query_plan
facts
answer_delta
completed
error
```

### 6.2 约束

- 必须先完成白名单查询并得到 `facts`，再开始流式生成自然语言。
- 前端先显示“正在查询真实数据”，收到 facts 后显示数字来源。
- 流式文本完成后执行数字一致性校验。
- 校验失败时用可信模板替换未通过的模型文本。
- 模型超时或断线时使用已获得的 facts 生成本地回答。
- 断开连接后停止模型生成，并保持消息状态可恢复。

## 7. 部署上线

### 7.1 部署结构

提供 Docker Compose：

```text
Nginx / React 静态文件
FastAPI / Uvicorn workers
只读 sales_clean.sqlite 数据卷
可写 app.sqlite 数据卷
服务器 Secret / LLM 配置
```

### 7.2 生产要求

- Nginx 统一代理 `/api`，生产环境不依赖宽松 CORS。
- API Key 通过部署平台 Secret 注入，不写入镜像或仓库。
- 清洗数据库只读挂载，对话数据库独立备份和持久化。
- 增加 `/health`、`/ready` 和数据库可用性检查。
- LLM 配置更新和连接测试接口增加鉴权。
- 配置请求限流、问答限流和最大并发数。
- 日志记录请求 ID、会话 ID、意图、查询耗时、模型耗时和回答状态。
- 日志禁止记录 API Key、完整提示词和不必要的用户数据。
- 配置超时、重试、熔断及本地降级策略。

## 8. 可观测性与可信度展示

增加内部质量指标：

```text
AI 请求总数
本地降级率
澄清率
无数据率
模型错误率
数字校验失败率
平均数据库查询耗时
平均首字响应时间
平均完整响应时间
```

前端每条回答显示：

- 数据来源。
- 查询条件。
- 回答状态。
- 是否使用本地降级。
- 数字一致性校验结果。
- 生成时间。

内部 SQL、系统提示词和密钥不返回前端。

## 9. 实施顺序

### 第一阶段：上下文与可信度

1. 新增上下文模型和增量查询计划。
2. 实现确定性的上下文合并器。
3. 扩充追问测试。
4. 建立独立 SQL 真值测试。
5. 生成 AI 数字一致性报告。

### 第二阶段：看板联动

1. AI 响应增加 `dashboard_target`。
2. 看板支持 URL 筛选状态。
3. 实现自动加载、滚动和高亮。
4. 增加端到端联动测试。

### 第三阶段：对比分析

1. 新增门店对比聚合服务和接口。
2. 增加 `store_comparison` 意图。
3. 建设门店对比页面。
4. 打通 AI 到对比视图的跳转。

### 第四阶段：体验与上线

1. 实现 SSE 流式响应和失败恢复。
2. 增加可观测性指标。
3. 增加 Docker、Nginx 和 CI 配置。
4. 完成权限、限流、Secret 和生产部署检查。

## 10. 测试计划

### 后端测试

- 上下文继承、替换、清空和澄清。
- 查询计划字段白名单校验。
- AI facts 与独立 SQL 真值一致。
- 回答数字提取和一致性校验。
- 错误模型输出自动回退。
- `dashboard_target` 只使用已校验字段。
- 门店对比指标和排序。
- SSE 事件顺序、断线、超时和降级。

### 前端测试

- 追问消息正确展示继承条件。
- AI 回答跳转后看板筛选正确。
- URL 参数刷新后仍能恢复。
- 无效 URL 参数显示提示。
- 门店对比选择、图表和空状态。
- 流式加载、停止、错误和本地降级状态。

### 端到端验收脚本

```text
1. 问“牛肉poke 六月卖了多少钱？”
2. 追问“那五月呢？”
3. 追问“S01 门店呢？”
4. 追问“订单数呢？”
5. 展开事实并核对继承条件和数据库来源。
6. 点击“在看板中查看”。
7. 确认看板自动应用 2026 年 5 月、S01 和对应指标。
8. 打开 AI 验证报告，确认全部用例数字一致率为 100%。
```

## 11. 验收标准

- 上下文追问测试全部通过，明确条件继承和覆盖结果。
- 固定 AI 真值测试集数字一致率为 `100%`。
- 不支持或无数据问题不生成虚构业务数字。
- AI 到看板的日期、门店和指标筛选完全一致。
- 门店对比支持 2 至 5 家门店，指标可由 SQLite 明细复算。
- LLM 超时或不可用时仍能返回本地真实数据答案。
- SSE 流式失败不会保存未经校验的最终回答。
- CI 中后端测试、前端构建、数字一致性测试全部通过。
- 生产配置不暴露 API Key，分析数据库保持只读。

## 12. 演示重点

最有说服力的演示链路：

```text
完整问题 -> 连续追问 -> 展示继承条件 -> 展开 SQLite facts
-> 显示数字一致性通过 -> 跳转看板并自动应用筛选
-> 打开门店对比 -> 模型断开后展示本地降级仍可回答
```

该链路同时证明系统具备自然语言交互能力、真实数据可信度、业务分析联动能力和生产可用的故障降级能力。
