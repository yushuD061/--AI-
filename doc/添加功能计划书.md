# 门店销售系统业务增强功能计划书

## 1. 计划目标

在现有门店销售看板、FastAPI 聚合接口、React 前端和 AI 数据问答基础上，增加真正服务运营日常工作的业务功能：发现异常、比较变化、定位门店和商品问题、生成日报、监控数据质量，并保证生产环境中的权限和操作可追溯。

本计划遵循以下原则：

- 所有营业额、订单数、客单价和销量均来自 `sales_clean.sqlite`。
- 新功能优先复用现有清洗口径和聚合服务，不在前端重复计算。
- 每项提醒都必须能回溯到日期、门店、商品和事实记录。
- 不增加当前数据无法支撑的客户画像、库存预测、利润分析和天气影响等功能。
- 先完成高频、可验证的运营功能，再扩展自动化和权限能力。

## 2. 功能总览与优先级

### P0：首批上线

1. 异常波动提醒。
2. 同比、环比和周期对比。
3. 门店经营排名与诊断。
4. 数据质量与数据新鲜度监控。

### P1：第二批上线

5. 商品结构和衰退提醒。
6. 运营日报和导出。

### P2：生产化上线前完成

7. 权限和操作审计。

## 3. 异常波动提醒

### 3.1 业务目标

帮助运营快速发现“哪里发生了异常”，避免每天只查看总营业额而错过门店或商品的突发问题。

### 3.2 异常类型

- 日营业额低于近 7 天平均值的设定比例。
- 日订单数低于近 7 天平均值的设定比例。
- 客单价高于或低于历史基线。
- 某门店连续多日无销售记录。
- 某商品连续多日无销售记录。
- 负金额或退款金额在某日、某门店集中出现。
- 营业额、订单数和客单价之间出现异常背离。

### 3.3 规则口径

第一版使用确定性规则，不使用模型猜测：

```text
基线：同门店近 7 个有效营业日
偏差阈值：默认 30%，可配置为 20%、30%、50%
最小样本：订单数少于 10 时不触发波动告警
连续无销售：默认 3 个有效日期
严重级别：info、warning、critical
```

### 3.4 后端接口

```text
GET /api/v1/alerts
```

参数：

```text
start_date
end_date
store_id
severity
alert_type
limit
```

返回：

```json
{
  "alert_id": "a_001",
  "type": "revenue_drop",
  "severity": "warning",
  "date": "2026-06-18",
  "store_id": "S01",
  "metric": "net_revenue",
  "actual_value": 3200.0,
  "baseline_value": 5100.0,
  "change_rate": -0.3725,
  "message": "S01 当日营业额较近 7 日基线下降 37.25%",
  "dashboard_target": {
    "start_date": "2026-06-18",
    "end_date": "2026-06-18",
    "store_id": "S01",
    "view": "trend"
  }
}
```

### 3.5 前端展示

- 看板顶部显示未处理异常数量。
- 异常列表按严重级别和发生时间排序。
- 点击异常跳转到对应日期、门店和图表。
- 支持标记已读，但不删除历史异常。
- AI 可基于异常事实解释可能原因，但不得生成 facts 之外的数字。

## 4. 同比、环比和周期对比

### 4.1 业务目标

回答“现在表现如何”和“相较之前变化多少”，避免只看单一时间区间无法判断增长或下滑。

### 4.2 对比模式

- 日环比：与前一营业日比较。
- 周环比：与前 7 个有效营业日比较。
- 月环比：与上一个自然月或相同天数区间比较。
- 自定义周期：用户选择两个日期区间。

### 4.3 对比指标

- 净营业额。
- 去重订单数。
- 平均客单价。
- 商品销量。
- 门店排名变化。

### 4.4 后端接口

```text
GET /api/v1/dashboard/compare
```

参数：

```text
current_start_date
current_end_date
previous_start_date
previous_end_date
store_id
```

返回当前值、对比值、绝对变化和百分比变化。除数为 0 时返回 `null`，不得返回无穷大或虚构百分比。

### 4.5 前端展示

- KPI 卡片显示当前值、对比值和变化率。
- 趋势图支持当前周期与对比周期双线展示。
- 支持切换“金额、订单、客单价”指标。
- AI 回答“六月比五月增长多少”时提供打开对比视图按钮。

## 5. 门店经营排名与诊断

### 5.1 业务目标

帮助区域经理和店长快速识别领先门店、下滑门店和需要辅导的门店。

### 5.2 排名指标

- 净营业额排名。
- 订单数排名。
- 客单价排名。
- 同比或环比增长率排名。
- 退款金额占比排名。

排名必须显示排序口径和筛选周期，金额相同按照 `store_id ASC` 稳定排序。

### 5.3 诊断内容

每家门店提供基于事实的摘要：

```text
营业额排名、订单数排名、客单价排名、周期变化率、主要贡献商品、主要下滑商品。
```

诊断只描述可由数据证明的事实，例如：

```text
S01 营业额排名第 2，订单数较上一周期下降 8%，客单价上升 5%。
```

不输出“管理不善”“员工服务差”等无法由销售数据证明的原因。

### 5.4 后端接口

```text
GET /api/v1/dashboard/store-ranking
GET /api/v1/dashboard/store-diagnosis/{store_id}
```

### 5.5 前端展示

- 新增门店排名视图。
- 支持切换排名指标。
- 点击门店进入该门店的趋势、商品结构和异常列表。
- 诊断卡片显示数据来源和计算周期。

## 6. 商品结构和衰退提醒

### 6.1 业务目标

不只展示 Top 10，还要识别商品结构变化和可能需要关注的商品。

### 6.2 功能内容

- 商品营业额和销量占比。
- 商品排名上升、下降和新进入 Top 10。
- 连续多日无销售商品。
- 商品在不同门店的销售差异。
- 商品退款或冲销集中提醒。
- 当前周期与对比周期的商品结构变化。

### 6.3 后端接口

```text
GET /api/v1/dashboard/product-mix
GET /api/v1/alerts/product-decline
```

### 6.4 前端展示

- 商品结构占比图。
- 排名变化表。
- 衰退商品列表。
- 点击商品跳转到日期、门店和商品筛选后的看板。

### 6.5 提醒规则

默认规则：

```text
当前周期销售额较对比周期下降 >= 30%
或连续 3 个有效营业日无销售
且历史周期至少有 10 个订单
```

规则必须显示实际周期、基线和样本数量。

## 7. 运营日报和导出

### 7.1 运营日报

日报默认包含：

- 净营业额。
- 去重订单数。
- 平均客单价。
- 表现最好门店。
- 表现最好商品。
- 营业额和订单异常。
- 与前一周期的变化。
- 数据更新时间和质量状态。

### 7.2 生成方式

- 页面手动生成。
- 后端按日期生成可复现日报。
- 日报内容保存版本号和数据日期。
- 同一日期重复生成时结果可追溯，不覆盖历史版本。

### 7.3 导出格式

第一版支持：

- CSV：明细和排名数据。
- XLSX：日报、门店排名、商品结构和异常列表。
- PDF：适合打印和汇报的日报摘要。

### 7.4 后端接口

```text
GET /api/v1/reports/daily
GET /api/v1/reports/daily/export?format=csv|xlsx|pdf
```

导出文件必须带有：

```text
数据周期、生成时间、数据版本、筛选条件、数据来源。
```

### 7.5 权限约束

导出范围不能超过当前用户可见门店范围，导出操作必须写入审计日志。

## 8. 数据质量与数据新鲜度监控

### 8.1 监控指标

- 原始文件最后更新时间。
- 清洗任务最后运行时间。
- 清洗数据库最后更新时间。
- 原始行数、有效行数和隔离行数。
- 缺失金额数量。
- 无效门店和商品外键数量。
- 重复销售行数量。
- 日期最小值和最大值。
- 最近有效销售日期。

### 8.2 后端接口

```text
GET /api/v1/data-quality
GET /api/v1/data-quality/runs
```

返回状态：

```text
healthy
warning
critical
```

建议阈值：

```text
超过 24 小时未更新：warning
超过 48 小时未更新：critical
隔离率超过 5%：warning
隔离率超过 15%：critical
清洗任务失败：critical
```

### 8.3 前端展示

- 看板显示“数据已更新于……”而不是固定文案。
- 数据质量页展示清洗运行记录。
- 数据异常时阻止生成误导性日报，并明确提示运营。

## 9. 权限和操作审计

### 9.1 角色

- 管理员：全部门店、配置、导出和审计权限。
- 区域经理：所属区域门店和区域报表。
- 店长：所属门店数据和门店日报。
- 只读访客：仅查看授权数据，不能导出和修改配置。

### 9.2 权限范围

权限控制覆盖：

- 门店数据查询。
- AI 问答范围。
- 异常列表。
- 报表生成和导出。
- LLM 配置。
- 对话删除。
- 数据质量查看。
- 审计日志查看。

后端必须在 SQL 查询层增加门店范围条件，不能只依赖前端隐藏选项。

### 9.3 审计事件

至少记录：

```text
登录和退出
AI 问答
导出报表
修改 LLM 配置
删除对话
查看或下载数据质量报告
修改异常状态
```

审计记录包含：

```text
event_id
user_id
role
action
resource
filters
request_id
created_at
result
```

禁止记录 API Key、完整提示词和不必要的敏感数据。

## 12. 验收标准

- 运营可以在一个页面发现异常，并跳转到对应日期、门店和商品。
- 任意对比指标都能由数据库明细重新计算。
- 门店排名和商品衰退提醒有明确周期、基线和样本数。
- 日报与页面 KPI 数字一致，导出文件可复核。
- 数据超过新鲜度阈值时，系统明确告警而不是继续显示“数据正常”。
- 权限在后端查询层生效，越权查询和导出被拒绝。
- 关键操作都有审计记录，且不泄露 API Key 或内部提示词。
- 不引入当前数据无法证明的业务结论。

## 13. 暂不纳入范围

以下功能暂不实现，除非补充可靠数据源：

- 会员画像和用户生命周期。
- 库存、缺货和补货预测。
- 成本、利润和毛利率。
- 天气、节假日和外部营销因素归因。
- 自动生成未经运营确认的经营决策。

## 14. 分阶段实施计划

### 阶段一：数据基础与异常可见性

**目标**：让运营能够确认数据是否可靠，并在看板中发现异常。

**依赖**：复用 `sales_clean.sqlite`、现有清洗任务和 FastAPI 聚合服务；不新增业务事实源。

**交付物**：

1. `GET /api/v1/data-quality` 和 `GET /api/v1/data-quality/runs`，覆盖更新时间、行数、隔离记录、缺失金额、无效外键、重复记录和日期范围。
2. `GET /api/v1/alerts` 及确定性异常规则，返回严重级别、实际值、基线、变化率、样本数和看板跳转参数。
3. React 看板的数据质量状态、更新时间、未处理异常数量、异常列表和联动跳转。

**验收**：验证近 7 个有效营业日基线、30% 默认阈值、订单数小于 10 不告警、连续 3 日无销售、零值和严重级别；数据过期时显示 `warning/critical`，异常点击能带上日期和门店筛选。

### 阶段二：经营分析

**目标**：支持周期比较、门店诊断和商品结构分析。

**依赖**：阶段一的统一筛选、数据质量状态和异常事实模型。

**交付物**：

1. `GET /api/v1/dashboard/compare`，支持日/周/月/自定义周期，除数为 0 返回 `null`。
2. `GET /api/v1/dashboard/store-ranking` 和 `GET /api/v1/dashboard/store-diagnosis/{store_id}`，支持稳定排序和事实诊断。
3. `GET /api/v1/dashboard/product-mix` 和 `GET /api/v1/alerts/product-decline`，覆盖占比、排名变化、跨店差异和衰退规则。
4. React 对比视图、门店排名/诊断视图、商品结构和衰退列表；AI 对比回答提供事实跳转目标。

**验收**：所有指标可由 SQLite 明细复算；金额相同时按 `store_id ASC` 排序；衰退规则同时校验下降比例、连续无销售和历史订单数；AI 不输出事实之外的数字。

### 阶段三：日报与导出工作流

**目标**：生成可复核、可追溯的日报和导出文件。

**依赖**：阶段一的数据质量和异常接口、阶段二的比较/排名/商品结构接口。

**交付物**：

1. `GET /api/v1/reports/daily`，保存数据日期和版本号，不覆盖历史版本。
2. `GET /api/v1/reports/daily/export?format=csv|xlsx|pdf`，文件带周期、生成时间、版本、筛选条件和数据来源。
3. React 日报生成、版本查看、下载和错误状态。

**验收**：日报数字与页面 KPI 及 SQLite 明细一致；重复生成可追溯；三种导出格式可打开并包含元数据；质量为 `critical` 时阻止生成正常日报。

### 阶段四：权限与操作审计

**目标**：在生产上线前完成后端数据隔离和关键操作留痕。

**依赖**：阶段一至三的所有查询、异常、日报和导出入口。

**交付物**：

1. 管理员、区域经理、店长、只读访客角色及门店范围模型。
2. SQL 查询层的门店范围条件，覆盖看板、AI、异常、日报、导出和数据质量。
3. LLM 配置、对话删除、导出和审计查看权限控制。
4. 登录、AI、导出、配置修改、对话删除、质量报告和异常状态变更审计事件。

**验收**：越权查询和导出被拒绝；前端不展示未授权门店和操作；受保护动作均有审计记录；日志不包含 API Key、完整提示词和无关敏感数据。

### 阶段执行规则

- 每阶段先完成后端接口、SQLite 复算测试和接口测试，再接入前端。
- 前端构建和关键流程验证通过后，才更新 `doc/PROJECT_PROGRESS.md` 中的完成度和状态。
- 计划内容不等同于实现状态；阶段一已于 2026-08-20 完成，阶段二至四仍为“未开始”。
- 继续使用 `sales_clean.sqlite` 作为唯一业务事实源，不实现库存、利润、会员画像、天气归因等当前数据无法证明的能力。

### 阶段一实施结果

- 已实现数据质量、清洗运行历史、确定性异常查询和异常已读状态接口。
- 已在 React 看板接入真实更新时间、质量详情、最近运行记录、异常筛选、已读切换和看板联动跳转。
- 后端及清洗测试共 20 项通过，前端生产构建通过；桌面和 390px 移动视口均无横向溢出，浏览器控制台无错误。
- 异常已读状态当前按全局范围保存；按用户隔离留待阶段四实现。
